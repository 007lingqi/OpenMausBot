# 钉钉研发助手产品与架构重设计方案

日期：2026-09-11  
版本：v1.0  
状态：方案草案，供产品、测试、项目经理和研发共同评审；不表示已实施或已上线。  
范围：个人和内部团队使用的自然协作入口，以及已授权非生产环境内的可验证研发交付。

## 1. 方案摘要

将产品重新组织为“一个理解上下文的群聊助手 + 一套持久、可恢复的研发交付流水线”。重设计对话与任务编排核心，保留已经验证有效的隔离、独立工作区、测试、来源追踪和幂等投递能力。

核心原则是：用户自然沟通，系统承担流程。普通用户不需要任务编号、技术命令、固定模板，也不必在多个机器人之间转述需求。

推荐方向：

1. 对外一个机器人，对内按需调用协作、开发和独立验证角色。
2. 一轮沟通统一处理理解、事实更新、问题接续和回复，避免各环节使用不同上下文。
3. 先调查已授权项目，再追问必须由人决定的业务问题。
4. 需求、执行、验证、交付和消息送达分别有事实依据，不用内部状态代替用户结果。
5. 权限与状态转换由程序执行；模型负责理解和建议，不授予权限、不自行认证完成。
6. 分阶段迁移，不一次性替换全部系统，不丢弃现有业务数据和验证证据。

本文件整理上一轮架构建议，并补充实现边界、迁移与验收约束。编写文档不构成生产部署、默认分支合并、身份变更或数据清理的授权，也不自动修改已有原生目标。

## 2. 产品目标与非目标

### 2.1 面向用户的成功结果

- 产品、测试、项目经理和研发人员能够直接在群里提出、补充、更正和跟进事项。
- 助手知道正在讨论什么，能接续短回答和方案选择；有歧义时用业务名称问清。
- 多人补充不会丢失，穿插话题不会串单；不能默认最后发言的人覆盖其他人的决定。
- 需求不清时只问会改变结果的关键问题，通常一个，最多三个；已回答内容不重复追问。
- 修改准确，测试覆盖业务要求、异常和边界场景，减少需求误解与测试遗漏造成的返工。
- 低风险修改在已有授权内自动完成；高风险或关键不确定项交唯一 Owner 决定。
- 回复简短、自然、结果优先；用户能明确知道修改范围、实际效果、验证情况或具体阻塞。
- 服务重启后能够接续，重复消息不会重复执行；主 Agent 不需要反复加载整段历史。

### 2.2 本次不做

- 不把钉钉文档、表格、附件读取、DWS 或互动卡片模板作为前置；已有能力和数据保留。
- 不自动生产部署、不自动合并默认分支、不自动 push、不扩展为多管理员或会签。
- 不以节省 Token 为目标降低模型能力，不无限增加 Agent 数量。
- 不要求机器人读取所有群消息；仅处理平台实际可达且位于白名单内的消息。
- 不通过绕过宿主权限、取消隔离、修改身份或删除历史来获得“完成”。

模型继续采用宿主 OpenCodex、gpt-6-astra、中等推理，复用已授权受限本机通道。更换模型不是本方案成立的前提。

## 3. 现状依据与问题判断

以下事实来自既有代码和试点记录，均限于相应版本与观察时点，不代表当前在线服务状态。

| 已观察的问题或事实 | 架构判断 | 对应设计 |
| --- | --- | --- |
| 固定过程回执、技术化结果、普通结果要求用户接受等问题曾反复出现 | 内部流程状态与用户交互混在一起 | 单一回复出口，按用户当前问题组织表达 |
| 模型已产生更具体的问题，但旧问题占据前三项展示位置；已有局部排序修复 | 理解、持久状态和展示缺少统一回合契约 | 同一回合产生事实增量、问题变化和回复依据 |
| “第二个”“按这个来”难以可靠接续 | 实际展示的方案及其上下文需要持久化 | 有来源、有版本的讨论与方案选择记录 |
| 真实记录中两条回复约82秒、50秒后发送；首次失败原因未保留 | 需要阶段耗时和安全错误分类，不能直接认定网络或模型为根因 | 端到端追踪、分类重试和非静默失败反馈 |
| 已有完整回归、独立复测及部分真实交付证据，但真实多人等验收仍有缺口 | 内部机制测试与真实产品体验必须分别证明 | 对话场景验收与研发交付证据双轨验证 |
| 开发过程曾被 Codex 工具权限审核超时阻塞 | 开发工具限制不等于钉钉业务审批，产品运行应与开发会话解耦 | 部署配置的运行身份与受限能力，不依赖桌面会话 |

需要避免两个误判：一是把所有问题归咎于模型；二是把所有安全机制当作交互障碍。真正需要调整的是职责、状态所有权和故障边界。

## 4. 架构选择与总体结构

### 4.1 推荐选择

采用模块化控制服务、持久数据库和独立执行进程或容器。初期可沿用现有技术栈与 SQLite，由控制服务集中提交业务状态；执行器通过受限接口回报结果，不直接拥有账本写权限。

相比只继续修补原有分散编排，这一方案能统一回合与恢复契约，但需要增量迁移和行为对照测试。相比立即引入独立工作流平台和多服务部署，运维与迁移成本更低；若后续实测出现多主机容量或高可用需求，再评估更重的基础设施。

暂不引入向量数据库、多个对外机器人、动态多 Agent 自组织或通用工作流平台。只有实测证明现有结构无法满足目标时，才增加这些组件。

### 4.2 职责视图

```text
钉钉群
  ↕ 白名单、身份校验、消息持久化
自然协作入口：理解、调查项目、回答、澄清
  ↕ 经校验的回合结果
事项中心：事实、问题、Spec、进度、证据
  ↕ 固定任务包和持久步骤
研发流水线：开发 → 独立复测 → 确定性验收 → 按授权交付

所有用户可见回复 → 统一回复出口 → 幂等投递 → 平台业务结果
所有状态变更     → 权限与版本检查 → 控制服务提交
```

这是逻辑职责划分，不要求每个方框独立部署。独立执行环境负责隔离故障与权限；数据库负责持久事实；模型上下文不作为权威状态。

### 4.3 角色与边界

| 角色/组件 | 负责 | 不负责或禁止 |
| --- | --- | --- |
| 群成员 | 提需求、补充、更正、查看进度 | 不能因发言获得 Owner 控制权限 |
| 唯一 Owner | 对具体高风险对象作决定，管理既定控制动作 | 不能用批准代替缺失的测试证据 |
| 协作 Agent / Meta | 需求理解、项目调查、问题接续、分解任务、整合解释 | 不自由执行任意命令，不自授权限，不自行写完成状态 |
| 开发 Agent | 在分配的工作区与范围内修改、自测、提交候选 | 不改共享控制规则，不写其他任务文件，不认证最终完成 |
| 独立 Verifier | 根据当前 Spec 核对候选，复测并检查遗漏 | 不直接接受开发者自报结论，不批准部署 |
| 控制服务 | 身份、策略、版本、任务调度、状态提交、验收门禁 | 不用模型建议覆盖硬约束 |
| 执行与部署适配器 | 在已配置能力内完成受限动作并提供真实回执 | 不继承开发者会话的无限权限 |
| 回复出口 | 根据可信事实生成并发送简短回复 | 不根据模型一句“完成”生成完成结论 |

## 5. 自然协作入口

### 5.1 统一回合处理

建议引入统一的回合结果契约，包含本轮涉及的事项、事实增量、问题变化、建议动作、回复依据和来源引用。具体字段在实现阶段定义，以下不是现有接口声明。

处理顺序：

1. 校验入站群与真实身份，持久化消息并去重；平台接收确认与群内回复分开。
2. 读取有界相关上下文：实际引用、已展示方案、当前事项、必要项目概览。
3. 模型产生统一的回合提案；需要调查时仅调用授权的只读能力。
4. 控制服务校验来源、对象、当前版本、字段范围和权限。
5. 在本地事务中提交被允许的事实变化与待发回复；需要执行的动作只进入持久队列，不在数据库事务中调用外部系统。
6. 回复出口根据提交后的事实发送；外部执行与投递各自结算结果。

事务提交时发现版本变化，应重新核对受影响内容，不发送旧结论，也不无限重复整个模型回合。统一回合不意味着只能调用一次模型，而是各步骤必须共享同一版本化结果。

一句话可以涉及多个事项或意图，例如“登录按方案修改，支付那个进展怎么样”。按子意图独立关联与检查；其中一个需要审批，不阻塞另一个只读查询，也不把局部成功说成整句全部完成。

### 5.2 讨论与实施

- 方案讨论保存为讨论记录，不自动变成代码执行任务。
- 明确独立修改请求创建 Work Item；普通用户不需要看到或填写编号。
- 保存真正展示的选项、来源回复、适用事项和版本，不能按后台候选排序猜“第二个”。
- 短回答只能作用于可靠关联的问题或方案；多个可能对象时用业务名称澄清。
- 选择方案不自动批准生产、合并、删除或身份变更；明确实施意图仍需满足执行策略。
- 显式无效引用不能被忽略，也不能自动转成新任务。

### 5.3 问题生命周期

每个问题绑定一个业务缺口，而不是一条临时文案。状态至少区分：未回答、部分回答、已解决、因更正被取代。

- 部分回答后沿用原缺口，只问剩余部分；不能不断追加同义问题。
- 已明确的事实直接进入当前记录，不为填内部字段重复确认。
- 改写后的 Spec 要保留来源；新增推断必须标为假设，不能借逐字引用证明不受支持的含义。
- 两人的要求冲突时保留两条来源，提出定向问题，不采用“最后写入覆盖”。
- 问题最多三个，优先会改变实施结果的决定；不要为了达到三项而补问。
- 谁应回答必须有真实依据；“产品负责人”等业务角色与机器人唯一 Owner 身份分开。

### 5.4 先查项目，再问人

为已绑定项目维护有版本的项目概览：功能模块、页面、接口、权限结构、测试入口、已知限制及未核实信息。每项概览应有源码或测试环境依据、观察时间和对应版本，不能凭模型记忆填写。

只读访问限定于已授权仓库与环境。没有项目绑定时先澄清项目；访问不可用时说明范围，不假装看过源码，不擅自进入生产环境。

业务示例：

> 用户：后台支持管理员，能按菜单配置，先覆盖当前所有业务。

系统应先调查已有业务模块，再追问尚未确定的菜单含义，例如：

> “按菜单配置”是指控制不同角色能看到哪些菜单，还是让管理员修改菜单内容？

这是一种期望交互，不预设用户已经选择其中任何一种，也不宣称项目已有这些能力。

## 6. 回复产品规则

默认以一至三句回答当前问题；必要的问题列表或方案对比可以适当展开。

| 场景 | 应提供的信息 | 应避免的内容 |
| --- | --- | --- |
| 查询进度 | 最新可核对进展、正在等待什么 | 新建任务、重新问一遍需求 |
| 澄清 | 剩余关键业务决定 | 固定开场、已解决问题、内部字段名 |
| 普通完成 | 改了什么、效果和已完成验证范围 | 要求“接受结果”、没有依据的上线结论 |
| 失败或受阻 | 哪一步未完成、是否已有影响、下一步 | 通用错误码、猜测原因、重复要求重发 |
| 方案咨询 | 简短建议、必要取舍 | 未经实施授权承诺动手 |

区分三种事实：代码修改完成、测试环境已更新、生产已发布。每一种说法都需要对应证据。

示例仅在证据真实成立时使用：

> 登录失败时现在会保留用户名、清空密码；错误提示已统一，相关回归已通过。

长处理超过配置阈值时，可发一次基于实际阶段的简短提示；快速完成直接给结果。固定收件回执不恢复为每条必发。具体阈值需依据真实响应基线确定，不承诺尚未验证的秒级体验。

模型可以组织措辞，但完成范围、批准对象、环境、测试结果和投递目标从服务端可信记录填入；不允许模型凭空生成这些事实。严格匹配不能证明语义自然，仍需真实对话评测。

## 7. 事项中心与上下文

### 7.1 单一事实来源

当前事项记录包含业务目标、已确认事实、未确认假设、问题与冲突、角色来源、Spec版本、当前步骤及证据索引。原始消息与不可变历史用于追溯，当前视图由持久记录生成。

SPEC、PROGRESS、DECISIONS、VERIFY 等文件可作为接管投影，但不能与数据库各维护一份竞争的当前状态。业务完成状态只能由控制服务修改。

### 7.2 分层上下文

1. 项目级：有版本的业务概览、受信权限及能力配置。
2. 事项级：当前需求、待解决问题、阶段、决策和必要证据索引。
3. 本轮级：当前发言、可靠引用、相关增量及实际已送达的机器人回复。

开发与验证角色只领取各自必要的任务包。完整历史、源码和日志按需检索；压缩不删除未解决问题或来源，截断也不能被解释为需求完整。

不把所有聊天内容自动存成永久个人记忆。记忆与事件记录分别设用途、权限和保留策略；敏感信息不进入模型、普通日志或 Git。清理与删除必须有明确授权和一致性策略，防止后台提取重建已删除内容；本方案不授权实际删除现有数据。

## 8. 研发交付流水线

### 8.1 固定任务包

每次执行绑定当前 Spec、项目与基线版本、允许和禁止的修改范围、可观察验收条件、验证方式、必要上下文、独立工作区与执行身份。

独立任务才委派；简单强耦合工作不为了多 Agent 而拆分。多个写入者不得共享工作区或并写同一文件，结果须携带候选版本、差异与测试证据。

### 8.2 三级验证

1. 开发 Agent 完成修改与自测，产出固定候选。
2. Verifier 在独立工作区读取 Spec 与候选，独立复测并检查异常、边界与遗漏，不以开发者总结代替检查。
3. Meta 的验收由程序核对当前 Spec、候选、验证契约、测试证据与修改范围；模型负责解释，不拥有最终完成写权限。

验收条件尽早映射到真实行为测试。测试使用稳定标识并绑定版本，标识本身不证明覆盖；关键断言要能发现对应缺陷。合并独立子任务后，针对最终整合候选执行完整回归，不能只合并各 Agent 的绿灯。

候选发生变化后，重新判断受影响证据，不沿用旧批准或旧测试认证新代码。增加补测应走显式候选修订，保留原 Spec、候选和尝试历史，不删除失败记录重新计数。

### 8.3 交付与通知分开结算

代码完成、验证通过、环境应用成功和消息送达分别持久化。向群里发送完成回复前核对当前版本；发送成功后记录投递证据。

若代码已完成而发送失败，仅恢复通知，不重新开发。若环境应用结果未知，先对账，不把超时直接当作失败，也不直接再次执行。只有约定交付范围及其证据齐全，才对外宣布该范围完成。

## 9. 权限与工具契约

### 9.1 授权分层

- 身份来自平台与受信配置，不能由模型参数、姓名、群消息或引用文字指定。
- 群成员可创建、补充和查询；暂停、恢复、重试、取消、接受、拒绝、部署、合并及身份配置等控制动作仅由唯一 Owner 发起。
- 已授权范围内低风险修改可自动完成；低风险判定需检查实际对象、差异、执行动作和策略，不由模型一句“安全”决定。
- 敏感、高风险或关键不确定项停在对应步骤，由 Owner 决定；其他独立的只读沟通仍可继续。
- 审批记录绑定真实主体、具体动作、对象版本或摘要及有效期；执行时重查。自然语言可以表达决定，但只有受信处理器能把有效决定转换为批准记录。
- 生产部署与默认分支合并始终需要对当前固定候选的明确批准；测试通过不替代批准。

### 9.2 建议能力契约

以下是逻辑接口建议，不是已经存在的工具名称。全部接口须校验结构、长度与结果数量；身份由服务端注入，审计不记录凭据。结果统一区分成功、规则阻塞、能力不可用、版本冲突与执行异常。

| 能力 | 调用主体与输入来源 | 前置与副作用约束 | 返回及幂等方式 |
| --- | --- | --- | --- |
| 读取项目概览 | 协作角色；受信项目绑定和版本 | 只读、限范围、返回来源与新鲜度 | 有界事实或不可用；不产生写权限 |
| 提交回合结果 | 控制服务；入站事件及模型提案 | 复核群、身份、来源、事项版本；事务内更新 | 按事件与子动作去重；冲突不部分提交 |
| 启动执行 | 调度器；已持久化的固定任务包 | 执行策略、版本、仓库租约和隔离均有效 | 持久步骤身份；重试先查已启动任务 |
| 登记验证结果 | Verifier适配器；固定候选与测试契约 | 校验证据来源、运行身份及候选未漂移 | 不可变结果；重复回报不重复推进 |
| 请求/应用审批 | 受信Owner入口及执行适配器 | 具体对象、版本、有效期、当前权限均匹配 | 独立审批与执行回执；拒绝不执行 |
| 发送业务回复 | 回复出口；服务端回读的事实和目标群 | 已授权群、去重键和当前回复事实有效 | 检查平台业务响应；未知结果先对账 |

协作模型不暴露通用任意 Shell、SQL、HTTP 或任意身份工具。执行角色可以在隔离工作区使用任务所需能力，但不能取得控制面数据库、部署凭据或宿主无限权限。关闭能力时同时从工具表与提示词移除，而不是假装支持。

## 10. 并发、故障和运行方式

- 控制服务独立常驻；产品日常运行不依赖开发者桌面解锁或当前 Codex 会话存活。
- 部署阶段配置明确的受限运行身份、项目能力和必要凭据；不通过自动批准或绕过宿主策略消除权限限制。
- 对话、执行和通知分别排队，长时间开发不能占住所有对话处理能力；并发额度与背压由实测配置，不使用无界队列。
- 同事项按版本提交，同仓库写入串行，不同仓库可并发；后来的关键需求更正使旧候选失去交付资格，并安全中断或结算旧执行。
- 服务重启后恢复未结算步骤，查询容器或执行进程真实状态；只有确认未执行的步骤才可重新发起。租约和围栏防止旧实例继续提交。
- 同一失败连续三次停止原路径，保留证据和恢复入口；不通过换任务、清库或换命令清零。
- 临时故障按分类有界退避；身份、策略、版本冲突与未知副作用不能按普通网络错误重试。
- Linux VM重启后的systemd恢复、宿主模型通道恢复及在途任务接续分别验证，不能互相替代。

最少观测信息：消息接收时间、排队耗时、模型开始与结束、状态提交、执行/验证阶段、回复提交及平台结果。使用关联标识串起链路，只保留安全错误分类与必要元数据，不记录 Secret 或无限制原始提示词。

“没回复”必须能区分未收到、排队中、模型失败、业务阻塞、投递失败与投递结果未知；平台发送成功也不等于已经目视确认客户端显示。

## 11. 分阶段实施与迁移

### 阶段一：自然协作闭环

交付统一回合、问题生命周期、实际选项上下文、项目概览和回复出口。以“后台、管理员、菜单配置”历史对话为样板，覆盖咨询、短回答、更正、查询和多人冲突。

先使用脱敏历史进行离线回放，新旧结果对照；回放模式禁止真实执行和外发。进入真实群前完成身份、注入、并发版本与回复去重的负向测试。退出标准是当前候选通过真实可见的对话场景，不仅是离线模型评分通过。

### 阶段二：一条真实研发交付路径

选择已授权项目中的低风险修改，从自然语言需求到固定候选、开发自测、独立复测、确定性验收及结果送达。随后覆盖需求中途更正、失败恢复、同仓库串行、跨仓库并发与Owner决策。

退出标准是完整业务证据链，以及真实平台、真实模型和执行环境分别验证。不能把只读咨询闭环作为研发交付完成，也不能替代整个产品目标。

### 阶段三：小范围切换和旧编排退出

按已授权群和新事项逐步切换。新旧引擎可以进行无副作用的影子分析，但同一事项仅有一个状态写入者、执行者和回复出口，通过持久所有权与围栏强制保证。

在途旧任务继续由原引擎完成，除非已验证明确的状态转换方案。迁移采用版本化适配和新视图，保留历史与原证据；先在独立副本检查数据一致性、兼容性、重放与重启。

发现越权、假完成、重复执行、需求丢失或无法解释的数据差异时停止扩大切换。停止新任务路由不代表取消在途工作；旧二进制不能理解新状态时，不直接回滚数据库，应停止接单、保留现场并前滚修复或使用经过演练且获授权的恢复路径。

旧编排退出前必须满足：所有在途归属已结清，真实场景通过，恢复演练完成，无新增未解释副作用，并取得本次整体目标要求的Owner最终人工确认。

## 12. 验收矩阵

| 目标/约束 | 对应设计 | 主要风险 | 验证方式 | 通过标准 |
| --- | --- | --- | --- | --- |
| C1自然新需求与低风险交付 | 统一回合、固定任务包、交付证据 | 假完成或多建任务 | 真实群提出请求并完成实际修改 | 无技术格式要求，结果能追溯当前Spec、候选和测试 |
| C2澄清与短回答 | 问题生命周期、方案上下文 | 重问、误解选择 | 部分回答、短同意、否定和更正对话 | 已解问题不重问，未解缺口保留，歧义先澄清 |
| C3多人补充更正 | 来源绑定、冲突记录 | 覆盖他人要求、伪造角色 | 至少两位真实群成员参与同事项 | 来源可追溯，冲突显式处理，提醒对象有依据 |
| C4穿插话题 | 多子意图、可靠关联 | 串单、错误实施 | 两事项交错、单句多意图、无效引用 | 正确接续；无效引用不创建替代任务 |
| C5查询解释致谢 | 事实约束的回复出口 | 查询触发开发、固定刷屏 | 真实查询、解释与致谢 | 简短回答当前问题，不产生开发副作用 |
| C6风险与Owner决定 | 受信身份、版本绑定批准 | 越权、旧批准误用 | 非Owner、过期批准、候选改变等负例 | 不执行被拒动作，不以批准替代证据 |
| 平台可达性 | 明确入站契约 | 假定能看到全部群聊 | 分别测试@、未@、引用回复 | 每种入口记录可达、不可达或未知，不凭无事件猜测 |
| 需求精确与测试覆盖 | 事实/假设分离、独立复测 | 把推断当需求、测试遗漏 | 模糊需求、冲突、异常及关键测试反例 | 关键不确定项不执行，测试能发现对应缺陷 |
| 并发与恢复 | 持久步骤、租约、围栏 | 重复执行、结果丢失 | 同/跨仓库任务、原事件重放、在途服务及VM重启 | 无重复副作用，同仓库串行，跨仓库可并发，重启可接续 |
| 注入与Secret安全 | 不可信上下文隔离、工具门禁 | 越权或泄露 | 群消息/引用/项目内容中的伪指令 | 即使模型服从伪指令，执行门仍拒绝；敏感值不外泄 |
| 迁移一致性 | 单写入者、影子分析、版本适配 | 双发、双执行、旧状态损坏 | 副本迁移、双引擎路由和恢复演练 | 原记录保留，同事项始终只有一个实际处理方 |

证据按三类保存：本地自动回归、真实模型评测、真实平台与执行试点。每条通过记录包含版本、配置、输入、结果和可复核产物；一种证据不能冒充另一种。

建议持续记录响应时间分布、重复追问率、错误归并率、一次交付率、需求返工率和测试遗漏率。先定义样本与统计口径、采集基线，再确定性能和质量目标；本方案不虚构现有容量或承诺未经测量的指标。

## 13. 实施前需关闭的未知项

| 未知项 | 关闭方式与责任 | 影响 |
| --- | --- | --- |
| 首个试点群与项目绑定是否明确 | 实施负责人只读核对现有配置；不清楚时由Owner选择对象 | 阻塞实际项目调查与执行，不阻塞文档评审 |
| 平台不同消息入口的实际可达范围 | 实施负责人和真实群成员共同记录客户端动作与回调 | 决定交互说明，不默认扩大监听 |
| 当前模型通道的延迟、容量和故障分布 | 实施负责人做有界、无真实副作用的测量 | 决定队列、并发和等待提示阈值 |
| 新旧状态的具体迁移适配 | 数据/控制面实现负责人编写映射并做副本演练 | 阻塞真实数据切换 |
| 运行身份可获得哪些正式能力 | 运维实施负责人核对宿主策略与现有授权 | 无法获得时应报告缺口，不以绕过权限替代 |
| 真实验收参与人与最终确认 | Owner安排真实参与者，最终由Owner本人确认 | 阻塞整体目标验收，不扩展为每项普通修改的前置 |

这些事项应由调查先行关闭，不一次性抛给用户填写问卷。只有确实改变范围、权限或结果的剩余选择才询问。

## 14. 与现有实现的衔接及依据
