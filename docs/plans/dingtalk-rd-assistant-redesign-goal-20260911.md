# 钉钉研发助手重设计：实施目标

日期：2026-09-11。原生 Goal 已创建并处于 active；本文是验收与接续记录，不是第二套运行状态。预算：未指定。

## Objective

执行[完整重设计方案](dingtalk-rd-assistant-redesign-20260911.md)，将现有系统升级为一个自然群聊入口、持久事项中心和可验证研发交付流水线。核心结果是需求理解准确、对话接续自然、回复简短可信、测试减少遗漏，主 Agent 可凭有界上下文继续工作。

## Scope 与交付

1. 自然协作：版本化统一回合；事实、假设、问题与冲突；实际送达选项接续；授权项目只读调查；多事项、多意图和自然回复。
2. 研发交付：当前 Spec、受限独立工作区、开发自测、独立 Verifier、程序验收；代码完成、环境应用和通知分别结算。
3. 迁移与运行：副本演练、无副作用影子对照、同事项单写入者、小范围切换；旧任务结清后退出旧编排。
4. 提交实现、自动化回归、真实模型和真实平台试点证据、恢复入口与最终验收记录。逐批交付不缩小整体目标。

## 非目标与约束

- 不要求钉钉文档、表格、附件、DWS 或卡片模板；不删除已有能力和历史。
- 不以 Token 节省降级模型；沿用宿主 OpenCodex / gpt-6-astra / medium 的已授权受限通道，不新增密钥。
- 普通低风险修改在已授权范围内自动完成，不要求用户接受结果。生产、默认分支合并、身份凭据、破坏性及不可逆动作依仓库规则对固定候选请求唯一 Owner 决策；不自动 push。
- 群白名单、真实身份、来源、版本、Owner 控制和 Secret 保护不降级；群聊、引用和项目资料不能授予权限。
- 保存后确认入站；发送检查平台业务响应；未确认的外部效果先对账再重试。
- 保留用户已有改动及未跟踪的 `outputs/`。本次实现不触碰无关支持邮件和账号用量事项。

## Autonomy 与停止条件

用户本轮明确授权生成 Goal 并实施方案。自主完成仓库内实现、隔离自动测试和合格批次本地提交；已授权受限本机模型通道按原对象范围复用。真实外发/部署前核对具体对象、候选与授权，不凭历史笼统“继续”扩大权限。

需要新增付费、凭据/身份变更、生产、默认分支合并、删除或不可逆影响时，仅停止相应步骤并请求唯一 Owner 明确授权；其他安全工作继续。关键不确定项先调查，不凭假设执行。同一失败连续三次停止原路径、留存脱敏证据并重新规划；原生 blocked 状态仅按宿主连续目标轮次规则设置。

## 首批实现与实际证据（2026-09-11）

### 已实现

- 问题区分未回答、部分回答、已解决与更正替代；部分回答必须保留剩余问题，更正替代必须有当前消息引用及本轮新问题，不能消除系统门禁。
- 状态变化由程序生成，和 Spec、澄清及 Outbox 在现有事务中保存为不可变回执；模型不能伪造状态回执或回答人身份。失败、过期和重放不产生新的问题历史。
- 从账本回执重建有界问题上下文：保留全部当前问题及最近 25 个关闭问题；更早记录不删除，校验问题 ID 时仍查询完整历史，避免截断后重新使用已解 ID。
- 不再把“本轮只展示三问”误当成“只允许回答这三问”：较早未解问题的自然回答也能被接收。
- 不添加数据库迁移，不写真实业务数据；旧快照无问题来源时标未知，不补造历史。当前兼容性范围不构成旧二进制可安全回滚/双写的承诺。

## 第二批：已送达方案的自然接续（2026-09-11）

已将“选第二个”、按方案名称选择和单一已选方案后的“按这个来”接入真实协作入口。新 `select_option` 动作只保存讨论决定，不创建 Work Item、Spec、执行记录或 Owner 权限。决定在原有事务中与回复一起提交，绑定发送来源、内容摘要、方案顺序、事项版本和 Spec 版本；提交前再次读取核对。消息重放不重复产生决定/回复，服务重启可接续。

上下文仅提供本轮可核对、此前已送达给相关发言人的讨论方案。不使用后台 Work Item 顺序推断序号；未发送、入站后才发送、跨群/无关联人员、失效事项版本、错误序号、模型伪造来源和提交前被改写的展示均不能成为有效选择。展示内容若被真实钉钉序列化长度限制截断，也不当成完整可选方案。显式跨人引用的全面接续仍待统一回合阶段实现，不把当前同人方案接续扩大宣称为 C3 完成。

回复采用已核对选项文字：首次选择只说明选中的内容，不重发全部选项；再次确认已选方案时只给短确认。多个选项下含糊“按这个来”会直接用方案名称澄清；“选第二个，不要执行”可以记录选择，不误作审批或开发授权。

## 第三批：明确实施请求与已选方案的来源绑定（2026-09-11）

### 实现范围

- 支持“请实现刚才选择的方案”和“选第二个，请开始修改”。模型必须提出明确实施意图和实际选项来源；同一个请求不再只处理为方案选择。仅选择或讨论不会创建开发任务。
- 无既有事项时创建一个事项；方案已关联事项时补充原事项，不重复新建。无关新需求不继承之前的方案；旧版本、已关闭事项、未送达/迟送达、跨群或无关联发言人、伪造来源及错误序号均不能绕过原门禁。
- 实施上下文从账本中已路由请求和已送达 Outbox 回读，包含当前请求原文、所选方案、来源与内容摘要。在需求解释完成后、Spec 事务提交前重新核对，防止模型等待期间来源变化。
- 需求模型可以引用所选方案的标题/描述作为验收材料；已确认目标只允许使用所选描述原文或既有严格来源规则，不认证模型扩写的目标。取舍文字不能直接冒充必做功能或权限。来源绑定不是执行授权、测试证据或 Owner 批准。
- 明确实施请求若漏带选项来源，不创建缺少具体内容的任务；数据属性顺序不同不再误判为来源被更改。带结束引号的描述不再被回复出口补出重复句号。

### 实际验证

- 原纵向用例先失败为 pending，随后打通选择→重启→明确实施→带来源 Spec，并验证重放不重复产生任务或解释。
- 新负例揭示遗漏来源仍可创建任务；修复后澄清而不变更需求。同一选择对象的字段排列导致自定义适配器误拒也由失败测试复现后修复。
- 完成 13 文件、465 项相关回归，覆盖意图、入站、需求投影、权限、通知、Outbox、平台发送器和实际序列化；另补 4 文件、99 项材料恢复/关联兼容回归。这不代表重新启用文档产品范围。
- 真实模型发现双句号后先补失败用例再修复；最后对受影响路径复验 4 文件、239 项通过。最终 `pnpm typecheck`、新模块及其测试的 oxlint、`git diff --check` 均退出 0。未声称全仓 lint 或本批完整 `pnpm test` 通过；最终发布整合候选仍需全回归。

- 沿着已送达选择的祖先方案和持久引用，回读相关用户讨论、机器人摘要及其来源；不依赖临时模型记忆，不把整个群的聊天都当成需求。用户原文保留真实主体、入账先后顺序和内容摘要，机器人摘要明确为 assistant，未选方案正文不作为新增验收引用来源。

- 模型投影最多保留 24 条来源、24000 字符，遍历最多 64 个唯一节点；重复来源去重。缺失或超限明确标记未完整核对，并形成不可被模型删除的上下文缺口，不能以截断后的片段认证需求齐全。原账本不删除。

## 第五批：有来源的事实与分歧保护基础（2026-09-11）

### 已实现及边界

- 需求解释提案可提交业务事实：稳定业务 key、业务标签、原文值、requirement/assumption 类型和当前原文引用。需求值必须包含在当前引用中，模型不能提交作者、完成状态或伪造持久事实回执。程序绑定真实作者、消息、结果版本及确定性 ID，在原 Spec 事务的不可变回执中保存。

## 第六批：原作者更正及旧验收来源清理（2026-09-11）

## 第八批：复合来源中的局部更正与可见确认（2026-09-11）
