## 目标

面向个人和内部团队的产品、测试、项目经理及研发人员，以钉钉群内自然对话完成需求提出、多人补充、疑问澄清、任务跟进和可验证研发交付。Meta 持续归并同一事项、保留已确认事实、区分新话题与补充，只追问 1–3 个会改变实现结果的问题；不要求普通用户填写任务编号、技术命令、仓库路径或固定模板。用户询问进度、解释结果或致谢时，不应被误当作新的代码修改需求。

回复像团队同事：简短、针对当前问题、有明确下一步；减少重复“已收到/已规划/待执行”播报。只有真实证据支持时才说“修改完成”，并明确改了什么、现在有什么效果、是否验证通过。普通低风险改动直接完成；高风险或关键不确定项只向唯一 Owner 说明动作、影响和风险，请求明确决定。自然表达不能代替服务端身份、版本、审批和幂等校验。

需求明确后仍须生成有消息来源的当前 Spec，隔离修改、开发自测、独立 Verifier 复测和 Meta 验收；同仓库写入串行、不同获准仓库可并发，重复事件不产生重复副作用，重启后继续同一事项。宿主模型固定 OpenCodex / gpt-6-astra / medium，不新增密钥或降级模型。

## 自然性判定

每段对话同时检查“理解正确”和“表达合适”，不能只检查关键词或测试数量：

1. 当前句子被识别为正确意图、事项和角色；没有丢失前面的已确认信息。
2. 追问必要、具体、最多三个，且回答后确实消除对应疑问。
3. 回复先回答用户当前问题，通常用 1–3 句；仅多项结果/审批确有需要时展开。
4. 默认不展示编号、状态枚举、Spec、候选、Ledger、绝对路径和技术重试命令。
5. 表述与后台事实一致，没有虚假的“开始了/完成了/失败了”，也没有把状态通知写成操作指导表。
6. 不因闲聊、查询、重复事件或不可信文本触发未经请求的修改。

测试分层：本地确定性回归保护权限/关联/状态与渲染；真实 Astra 对话评测检查模型理解；真实钉钉多轮试点检查平台投递、上下文和可见回复。各层分别记录，替身模型或模拟渲染不能冒充后两层通过。
